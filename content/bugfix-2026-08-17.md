# 一次全面的代码审计：修了 6 个 Bug

今天对整个项目做了一次代码审计，从前端到后端到 Python 客户端，逐文件过了一遍。总共找到并修复了 6 个 bug，按严重程度排列如下。

---

## Bug 1（严重）—— 状态管理页面永远显示"离线"

**文件**：`public/managers/status/index.html`

**问题**：`GET /api/data` 返回的是 `{ devices: [...] }` 格式（设备数组），但管理页面的 `loadStatus()` 把返回值当成单个状态对象来用：

```js
// 之前（错误）
const status = await api('GET', '/api/data');
if (status.active) { ... }  // status 是 {devices:[...]}，没有 active 属性
```

**修复**：改为正确解析 `devices` 数组，遍历显示所有在线设备：

```js
// 之后（正确）
const data = await api('GET', '/api/data');
const devices = data && data.devices ? data.devices : [];
if (devices.length === 0) { /* 离线 */ }
else { /* 遍历 devices 显示 */ }
```

## Bug 2（严重）—— 状态管理页面 XSS 注入漏洞

**文件**：`public/managers/status/index.html`

**问题**：配置项的删除按钮使用了内联 `onclick` 处理器，用户输入的值被直接拼进 JS 字符串：

```html
<!-- 之前（危险） -->
<span class="tag-remove" onclick="removeBlacklist('${escapeHtml(item)}')">
```

`escapeHtml` 只转义了 `& < > " '`，但没有转义反斜杠。攻击者可以构造 `\');alert(1);//` 来注入任意 JS 代码。

**修复**：改用 `data-*` 属性 + `addEventListener` 事件委托：

```html
<!-- 之后（安全） -->
<span class="tag-remove" data-action="removeBlacklist" data-value="${escapeHtml(item)}">
```

所有内联 `onclick` 处理器全部移除，改为统一的事件委托：

```js
document.addEventListener('click', async (e) => {
  const btn = e.target.closest('.tag-remove');
  if (!btn) return;
  const action = btn.dataset.action;
  // 根据 data-action 分发处理...
});
```

## Bug 3（中等）—— Python 客户端登录请求格式不匹配

**文件**：`client/status_client.py`

**问题**：客户端登录时用了 `as_form=True`，发送的是 `application/x-www-form-urlencoded` 格式。但服务器使用 `express.json()` 中间件，只解析 `application/json`。结果服务端 `req.body` 为空，Zod 校验失败返回 400。

```python
# 之前（错误）
self.http.request("POST", "/api/login", {...}, as_form=True)

# 之后（正确）
self.http.request("POST", "/api/login", {...})
```

---

## Bug 4（中等）—— Python 客户端退出时不清除设备状态

**文件**：`client/status_client.py`

**问题**：退出时上报 `{"active": False}` 但没带 `deviceName`。服务端会用 `username_default` 作为 deviceId，如果客户端使用的是自定义设备名，该设备的状态不会被清除，前端会一直显示该设备"在线"直到超时。

```python
# 之前（遗漏）
self.client.report_status({"active": False})

# 之后（正确）
self.client.report_status({"active": False, "deviceName": self.client.get_device_name()})
```

## Bug 5（低）—— 管理页面缺少角色校验

**文件**：`server.js`

**问题**：`requireAdminPage` 中间件只检查了 session token 是否有效，没有检查用户角色。任何已登录用户都能访问 `/managers/` 下的管理页面 HTML（虽然 API 层有 `requireAdmin` 拦截，但页面本身可以被查看）。

```js
// 之前（不完整）
if (verify(token)) return next();

// 之后（完整）
const session = verify(token);
if (session) {
  const user = db.prepare('SELECT role FROM users WHERE id = ?').get(session.userId);
  if (user && user.role === 'admin') return next();
}
```

## Bug 6（低）—— Python 客户端 GetTickCount 溢出风险

**文件**：`client/status_client.py`

**问题**：`GetTickCount()` 返回 32 位毫秒数，系统运行 49.7 天后会溢出回绕，导致空闲时间计算错误。改用 `GetTickCount64()`（Windows Vista+ 支持），64 位毫秒数在可预见的未来不会溢出。

```python
# 之前
return (kernel32.GetTickCount() - lii.dwTime) / 1000.0

# 之后
GetTickCount64 = kernel32.GetTickCount64
GetTickCount64.restype = ctypes.c_uint64
return (GetTickCount64() - lii.dwTime) / 1000.0
```

| Bug | 严重程度 | 涉及文件 | 类型 |
|-----|---------|---------|------|
| 状态管理页面数据格式 | 严重 | status/index.html | 逻辑错误 |
| XSS 注入漏洞 | 严重 | status/index.html | 安全漏洞 |
| 登录请求格式不匹配 | 中等 | status_client.py | 接口不一致 |
| 退出不带 deviceName | 中等 | status_client.py | 逻辑遗漏 |
| 管理页面缺角色检查 | 低 | server.js | 权限不严 |
| GetTickCount 溢出 | 低 | status_client.py | 边界情况 |

这次审计的教训：前后端接口格式要统一，内联事件处理器是 XSS 的温床，权限检查要在每一层都做。
